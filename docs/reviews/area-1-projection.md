# Area 1 — Channel state and projection: review brief

Branch: `area/projection` · Spec: `docs/specs/3-channel-state-and-projection.md` · Tests: 50 passing on `swift test` (per the branch's changelog line; not re-run for this brief) · CI: not yet run on this branch

## What the spec asked for

Spec 3 defines what is on a channel at any moment (`ShowState`, §2), how tracked attributes behave across writes and list boundaries (§3), what each kind of write does (§4), how the live pointer moves and triggers arm (§5), and the one pure function that computes all of it: `project(state, commands, context) -> (state, effects)` (§6), run from three starting points (§7) with lock decided by the command's source (§8). It fixes a 24-row test table (§9) to be written before the code, and the Swift shape (§10): value types only, Foundation only, no clock, no traps on bad input, a doc comment per public function quoting its spec section. Specs 1 and 2 supply the object and command shapes the projection reads.

## What was built

`core/` now has three groups. `core/State/` is the value of the show: `ShowState` (channels, outputs, stacks, pointer, armed, popups), `ChannelState` (content, provenance, outgoing instances, attributes, lock), the five content instances (`ContentInstance.swift`), and `Tracked<Value>` with its origin and shadow (`Tracked.swift`). `core/Commands/` is the Spec 2 vocabulary as one `Command` enum with a case per row of the §3 table, plus `ContentExpression` (what a write asks for), the riders, `CommandSource`, `Guard`, and a `JSONValue` for the reserved `edit` command. `core/Library/` holds the slices of Spec 1 the projection reads: `Library` (channels, transitions, audio transitions, lists, macros) and `Machine` (stacks, outputs, playlists, local lists, tracking switches, default decoder cap). `core/Projection/` is the function: `Projection.swift` dispatches each command to a method on a private `Fold` value, `+Tracking` holds the §3 rules, `+Channels` the §4 write semantics and channel verbs, `+Pointer` the §5 pointer and triggers, `+Outputs` stacks and popups, `+Macros` macro inlining and guards, and `Effect.swift` the §6 effects. There is also a small public `lookahead(state, steps, context)` for the §7 offset-slot base.

A caller builds a `ProjectionContext` (frame, frame rate, library, machine, missing media ids, source, a variables closure), calls `project`, keeps the returned state, and acts on the effects. Nothing else is needed to use it.

Everything is a struct or enum; the only `import` in `core/` is Foundation; there is no `class`, no `Date()`, no randomness, no `fatalError`, `try!` or force-unwrap anywhere in `core/`. Every public type and function carries a doc comment quoting its spec section, except the `encode(to:)` halves of the hand-written `Codable` conformances, which are boilerplate.

## Choices made where the spec left room

- **Where:** §2 lists `build` among the tracked attributes, but §3 rule 8 calls it "an attribute of slide content" and §4 Slide says a new build "changes only `build`". **Options:** a `Tracked<Int?>` attribute with origin and shadow, or a field on the slide instance. **Chosen:** on `SlideInstance.build` (`ContentInstance.swift`, `ChannelState.swift`), so a build index is content state: it is not reset by a list boundary and has no origin. **Why:** rules 8 and §4 describe exactly that, and a build has no meaning once the content changes. **Reversible?** Yes, but the spec should say which it is (see Deviations).
- **Where:** §4 Text says identical text is a `noop` with "no state change", but §9 row 5 writes `text "y"` over `y` carrying `grade 6 once` and expects grade 6. **Options:** make identical content a pure noop (row 5 fails) or let riders apply even when the content is unchanged. **Chosen:** riders always apply; a write is a `noop` only when nothing at all changes (`Projection+Channels.swift`, `write`). **Why:** row 5 is the spec's own example. **Reversible?** Yes; one branch.
- **Where:** §4 Decoder budget, "the frame their transition ends, which it can compute from the transition duration and the landing frame", needs a frame rate the context does not list. **Options:** assume 60 fps, or carry the machine's rate. **Chosen:** `ProjectionContext.rate` (`FrameRate {num, den}`, Spec 1's shape), with ms rounded to the nearest frame (`ProjectionContext.swift`). **Why:** rows 14, 20 and 21 need ms turned into frames and the machine is not always 60 fps. **Reversible?** Trivially.
- **Where:** §4 Decoder budget does not say what a cut does to the outgoing list, yet row 14 expects "outgoing is B" after a cut from B to C. **Chosen:** every write over media records the previous instance as outgoing, ending at landing frame + transition frames, so a cut's outgoing ends on the landing frame and is dropped at the next write; a same-ref restart records nothing (it keeps its decoder); only media enters the list (`replaceContent`). **Why:** it is the only reading under which row 14 holds. **Reversible?** Yes.
- **Where:** §6's effects table has no row for transport, end behaviour, lock or freeze, but says "every command in, one result out" and Spec 2 §8 lists `ok` as a result. **Options:** emit nothing (breaks totality), emit `noop` (wrong: state changed), or add an effect. **Chosen:** `Effect.applied(Command)`: the command changed state with nothing to animate (`Effect.swift`). **Why:** keeps the fold total and the log honest. **Reversible?** Yes; see Deviations for the spec line to add.
- **Where:** §5 defines two pointer shapes; `playlist "TITLE"` (Spec 2 §3) makes a playlist live "without firing it", which is neither. **Chosen:** one `LivePointer` struct with optional fields; a loaded playlist is a pointer with only `playlist` set, so the first `next` fires cue 1 as a boundary (`ShowState.swift`, `Projection+Pointer.swift`). **Reversible?** Yes.
- **Where:** §6 says `machine` is "stacks, outputs, tracking switches", but `next` has to walk the playlist and resolve local copies. **Chosen:** `Machine` also carries `playlists`, `localLists` and `decoderCapDefault`; `Library` carries only the Spec 1 fields the projection reads (channels, transitions, audio transitions, lists, macros), with a note that Area 2 fills the rest (`Library.swift`, `Machine.swift`). **Reversible?** Additive.
- **Where:** `grade` has no "none" value in §2 beyond "the default grade is none". **Chosen:** `Tracked<Int>` with 0 meaning none, as Spec 2 §3 says (`grade 0` means none). **Reversible?** Yes, but `Int?` would complicate every comparison for no gain.
- **Where:** Spec 1 §6 and Spec 2 §4 give the object form but not the Swift shape. **Chosen:** `Command` is an enum with a case per vocabulary row and a hand-written `Codable` that writes `cmd` as `target.verb` and the parameters as flat keys; riders are a `Riders` struct of optional typed riders written as sibling keys of the write; `Target` is a number or `all`; an unknown `cmd` decodes to `.unknown` rather than failing, so a loader keeps it and the projection answers `noop` (`Command.swift`, `ContentExpression.swift`). **Why:** matches Spec 1 §6's worked example byte for byte (there is a test that decodes it). **Reversible?** The enum is the right shape; the field names can change with the parser in Area 3.
- **Where:** what a write asks for versus what is on the channel. **Chosen:** two types, `ContentExpression` (the request: ref, in, out, loop, gain, sync, build) and `ContentInstance` (the result: adds startedAtFrame, transport, endBehavior, missing). **Why:** §4 says the instance is derived from the expression plus the landing frame. **Reversible?** Yes.
- **Where:** rider effects and their order. **Chosen:** riders are applied before the transition is chosen, so a `track` transition rider governs its own write (it has become "the channel's current attribute" by then), and the `attribute` effects for riders are emitted after the `transition` effect. A redundant attribute write (same value, origin becomes tracked) still emits an `attribute` effect with old equal to new, so chips can show "redundant". **Reversible?** Ordering only.
- **Where:** `system clearall` and lock. Spec 2 §3 says clearall passes lock. **Chosen:** clearall clears each channel with source `engine`, using that channel's current transition for the dissolve, then resets attributes, in channel order (`clearAll`). **Reversible?** Yes.
- **Where:** `next` past an item whose list has no cues. **Chosen:** skipped like a header. **Why:** firing nothing is not a position. **Reversible?** Yes.
- **Where:** §6 `boundary` carries "list entered, attributes reset". **Chosen:** `(list, reset: Bool)`; the per-attribute detail is already in the `attribute` effects that follow. Row 8's "no boundary reset list" reads as `reset: false`. **Reversible?** Yes.
- **Where:** `stack N blackout` uses "the output's blackout transition" but a stack may be on several outputs or none. **Chosen:** the first output (by number) currently showing the stack, else nil (`Projection+Outputs.swift`). **Reversible?** Yes.
- **Where:** popups: `clearafter` is a timer, and timers are not state. **Chosen:** `Effect.variable` carries `clearAfterMs` for the scheduler; `popups[N]` holds only the text. **Reversible?** Yes.
- **Where:** `audio N mute` and `channel N skip | back` have no home in ShowState. **Chosen:** `passthrough`, like timers. **Why:** audio-output mute is engine state (Spec 4 §11); audio sets are v1.5. **Reversible?** Yes, when the state grows.
- **Where:** Spec 2 §7 guards read values by name. **Chosen:** state-derived values (`Popup N`, `Channel N Content | State | Lock`, `Output N Stack`, `Stack N Blackout`, `Live Item | Cue | Title`) come from the fold; everything else (`Timer N`, `Time`, `Date`) from the context's `variables` closure. `Channel N Content` renders as "kind: label" (`Projection+Macros.swift`). **Reversible?** Yes.
- **Where:** JSON for integer-keyed maps. Swift writes `[Int: V]` as a flat array, which breaks Spec 1 §5. **Chosen:** `IntKeyedCoding` writes them as objects with decimal string keys; `StackState.muted` is a `Set<Int>` written sorted. **Reversible?** No need.
- **Where:** Spec 1 §10's fixture library on disk does not exist yet. **Chosen:** `tests/OCoreTests/Fixtures.swift` builds the library in code with fixed UUIDs (seven lists, one playlist with headers, two macros, two stacks, two outputs). **Reversible?** Area 2 replaces it with files; the tests keep their shape.
- **Where:** macro command name. Spec 1 §6 writes `{"cmd": "macro", "macro": 12}`; Spec 2 §3 says `macro.run`. **Chosen:** decode both, print `macro.run`. See Deviations.

## Deviations and spec corrections

1. **Pool-item defaults are not applied.** §4 Media says in/out/loop/gain/sync fall back "to the pool item's defaults, then to none". The context has no media index, so the code goes straight to none. Fix: Area 2 adds the media index (Spec 1 §7 entries with `defaults`) to `ProjectionContext.library` and `write` consults it, with a test. Until then a caller must resolve pool defaults into the expression itself. This is the one functional gap.
2. **`{"cmd": "next"}` does not decode.** Spec 1 §6 shows `{"cmd": "next"}`, but Spec 2 §3's object column says `playlist.next`, and the decoder accepts only the Spec 2 names (it special-cases `macro` alone). A list file written in the Spec 1 style would load `next` as `.unknown` and the projection would answer `noop`. Fix: align Spec 1 §6's examples to the Spec 2 object names (`playlist.next`, `macro.run`), and have Area 3's parser accept the bare verbs on input.
3. **§2 lists `build` as a tracked attribute; the code keeps it on the slide instance.** Proposed wording for §2, tracked attributes row: `grade`, `transition`, `audioTransition`, `gain`, `chase` (reserved); and one sentence under Content: "`build` is part of slide content (§3 rule 8)".
4. **`applied` is not in the §6 effects table.** Proposed row: `applied` — command — "State changed with nothing to animate (transport, end behaviour, lock, freeze); logged as `ok`".
5. **`ProjectionContext.rate` is not in §6.** Proposed: add `rate` ("the machine's frame rate, `{num, den}`, so durations become frames") to the §6 list.
6. **`machine` in §6 is wider than written.** Proposed: "`machine` (stacks, outputs, playlists and local copies, tracking switches, decoder cap default)".
7. **Minor:** `Effect.variable` carries `clearAfterMs` and `boundary` carries a Bool; both are readings rather than contradictions, but the §6 table could say so.

Nothing else departs from the spec's letter: tracking rules 1–9, the §4 write semantics for every kind, missing media, transition selection order, the boundary definition, `next`/`previous` across items and headers, library-list live mode, armed state with shorter-wins and manual-fire disarm, section jumps, lock for `cue`/`timeline` sources only with macros inheriting `cue`, and `lock`/`unlock` never blocked are all implemented as written.

## How the tests prove it

`tests/OCoreTests/ProjectionTableTests.swift` has one test per §9 row, named `test_rowNN_…`, and every row matches its setup, commands and expectation:

- Rows 1–3 (media write, same-ref restart, identical text noop): exact effect lists asserted; row 2 also checks the restart adds no outgoing instance.
- Rows 4–6 (track, once with shadow, once transition falling back to default): attribute values with origin and shadow asserted after each command; row 6 checks ref 2/500 ms then ref 1/0 ms.
- Rows 7–8 (boundary reset, trackThrough): fired through `list N cue M` into L2 and L6; grade, content and pointer asserted; row 8 asserts no `boundary(reset: true)`.
- Rows 9–11 (clear, clearall, reset): exact effects; row 10 also checks the outgoing bookkeeping and that all three channels got a transition.
- Rows 12–13 (lock from a cue group, ignored from osc): blocked effect first, other channel written.
- Row 14 (decoder budget): outgoing A ending at 160 after B, then `steppedOn A`, outgoing B, content C, exactly as the table reads.
- Row 15 (tracking switch off): once, then default.
- Rows 16–17 (`next` at the end, `next` across a header into a different list): noop and unchanged state; pointer on item 5 cue 1 with boundary and reset.
- Row 18 (lookahead): +1 and +2 both z, frame held (channel 1's media starts at the held frame), +3 nil.
- Row 19 (slide builds): transition, build 2→3, noop.
- Rows 20–21 (Time trigger arms at 400, manual fire disarms; shorter wins, tested both ways).
- Row 22 (stop rewinds, noop on text): asserts the `applied` effect for the media channel.
- Rows 23–24 (passthrough, determinism).

`ProjectionSupplementaryTests.swift` covers what §3–§8 say outside the table: macro inlining with a state guard and with a context variable (durations compared as durations), a macro fired by a cue obeying lock while the same macro from a key does not, unknown macro, output stack switch with its switch transition and noop on unknown stacks, blackout toggle with the showing output's transition, per-channel mute, popup set and clear, end behaviour and pause, missing media, `all` expanding in number order, every pass-through and unknown command, and lock surviving reset, clearall and a boundary while `unlock` from a cue is never blocked. `DeterminismPropertyTests.swift` runs 300 seeded random sequences for determinism, 300 for "a group folds the same as one command at a time", and 300 for "every command yields at least one effect". `ShowStateCodableTests.swift` round-trips a fresh, a busy, an input/empty and a folded state, checks the JSON uses string-keyed objects with absent nil shadows, rejects an unknown content kind, round-trips a corpus covering every vocabulary row, decodes Spec 1 §6's worked example, and round-trips a guarded command. `ImportRuleTests.swift` is the Foundation-only lint.

Deliberately not covered yet: the §10 replay test ("fold a recorded log from the fixture") needs the fixture library and a log format, both Area 2; `item N section`, `playlist "TITLE"`, `previous` and `freeze` have no direct test (they are exercised only by the random sequences); pool-item defaults (deviation 1). ## Swift notes for this area

Value semantics: every type here is a `struct` or `enum`, copied on assignment, so `project` cannot change the state it was given; tests do `var before = F.fresh()` and edit the copy (`ProjectionTableTests.swift`). Enums with associated values: `ContentInstance.media(MediaInstance)` carries its payload inside the case, and `if case .media(let m) = current` pulls it out (`ContentInstance.swift`, `Projection+Channels.swift`). `Codable` synthesis versus hand-written: `Tracked` and `MediaInstance` get their JSON for free; `ContentInstance`, `Command` and `ShowState` write their own `init(from:)`/`encode(to:)` to get the `kind` key, the `cmd` key and string-keyed maps the specs want (`IntKeyedCoding.swift` is the helper). `Sendable` on every type and `@Sendable` on the variables closure is Swift 6's promise that a value can cross threads without a lock (`ProjectionContext.swift`). Extensions: `Fold` is one type split across five files with `extension Fold { … }`, one per spec section (`core/Projection/`). `mutating func` and `inout`: a method that changes a struct is marked `mutating`, and `applyRider(&channel.attributes.grade, …)` passes the field by reference for the duration of the call (`Projection+Tracking.swift`). Optionals and `guard let`: `state.channels[number]` is `ChannelState?` because the channel may not exist; `guard var channel = … else { return false }` is the "unknown input is a noop" rule in one line. Generics: `Tracked<Value>` is one struct used for Int, Double, Bool and `TransitionSetting`.

## For Adam to decide

1. **Approve with the spec corrections above applied?** Recommended: yes. Items 3–7 are wording; item 1 is Area 2's job and is written into its prompt; item 2 is Area 3's parser plus a Spec 1 wording fix. None changes the code on this branch.
2. **Pause and resume.** `channel N pause` then `play` leaves `startedAtFrame` at the original start, so the engine cannot know from ShowState alone where a paused clip resumes; `stop` does reset it. Spec 3 puts playhead arithmetic out of scope. Recommended: leave ShowState as it is and let Spec 4 own per-instance playheads in the engine, with one sentence added to Spec 3 §4 Transport: "`play` after `pause` resumes from the engine's playhead; `startedAtFrame` is reset only by a write or `stop`". The alternative, a `pausedAtFrame` field, would make lookahead and replay carry engine detail they do not need.
3. **Build order for Areas 2 and 3.** The projection consumed enough of Spec 1 and Spec 2 to define the object and command shapes. Recommended: keep Area 2 next as planned (it fills in the rest of the Spec 1 types, the loader and the fixture library that the replay test and deviation 1 need), then Area 3 (parser/printer, OSC mapping) on top of the `Command` enum as it stands.
